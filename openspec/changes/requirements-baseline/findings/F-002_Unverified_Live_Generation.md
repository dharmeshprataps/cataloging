## Summary

242 tests pass. The full conversation completes end to end over HTTP. And **not
one real image has ever been generated by this system.**

Every generation test runs against `FakeImageProvider`, which returns a
synthetic PNG. The live smoke test exists (`scripts/smoke-gemini.ts`) but has
never been executed, because no `GEMINI_API_KEY` has been available. `[OBSERVED
EVIDENCE]`

This is the largest uncertainty in the project and it is not a technical one. The
code may be correct in every respect while the product is worthless, because the
one thing nobody has looked at is the output.

The same substitution is the reason four requirements are `unverified`
(`GEN-001`, `GEN-008`, `GEN-009`, `SIM-008`): no test constructs
`GeminiImageProvider`, so the adapter's own call shape, retry loop and
policy-refusal branch are never executed. `PROBLEMS.md` records them.

## The specific claim that is unverified

> A photograph of a garment, taken on a hanger or a mannequin, can be turned into
> a convincing catalogue image of that same garment worn by a model, at a quality
> a small brand would publish.

`HYPOTHESIS`. **Falsification test:** run the smoke test on three real garments —
ideally one with a complex print, one plain dark fabric, and one with fine
detail such as a lace trim — and judge whether the print, colour, and silhouette
survive. Complex prints and dark fabrics are where general image models fail
first.

## Why this matters more than the other findings

- Every quality-related decision is currently guesswork: the prompt layers
  (`GEN-003`), the revision-versus-regeneration strategy (`DEC-0003`), the model
  choice and its documented legacy status (`DEC-0002`), and whether the
  unused vision pass (`F-001` F3) is the fix.
- Roadmap priority cannot be set rationally. Improving fidelity is only the
  right move if fidelity is the problem.
- The cost model is unvalidated: `estimateCostUsd()` is a hardcoded table
  (`MED-011`), never checked against a real invoice.

## What is verified instead — and what that is not

Verified: the API call shape, against the installed SDK's type declarations;
multi-reference input; chained edits; response parsing including a fallback that
walks the response step tree; retry and policy-refusal classification; timeout
handling; media validation against real PNG and JPEG bytes.

**None of that is evidence about output quality.** A correct call producing a
mediocre image is the expected outcome of an unvalidated prompt strategy.

## Access limitation

No API key has been available in the development environment. This is an access
constraint, not a scheduling choice, and the spec records it as such rather than
implying the check was merely postponed.

## Required action

1. Provide a `GEMINI_API_KEY`.
2. Run `./run.sh pnpm smoke:gemini` — one real call, writes to `data/smoke/`.
3. Run the same three garments through the full conversation and judge them.
4. Only then set quality roadmap priority.

## Interaction with the spec's own honesty

This finding is the reason `DEC-0005` chose baseline mode. A specification that
described the image quality as satisfactory would be false, and a gate that
passed it would be worthless. `spec.md` marks quality requirements `verified`
**only** where tests prove mechanism, never outcome — and this artifact states
plainly which claims remain open.

## Status

OPEN, blocked on access. Not a defect in the code. **Not resolvable by any
amount of further development** — only by looking at real output.
